Halo's `mods/halo-genie.wh.cpp` is a fork of MacOS Minimize Animation, but its current DirectComposition renderer uniformly scales a snapshot; it does not implement a genie mesh. Maximize/unmaximize use separate zoom tracks. `src/swoop.cpp` is a DWM thumbnail scale fallback for processes the mod cannot reach, and restore through this path is triggered by a dock click. These are distinct paths and require separate verification.

## Timing and shape debugging, 2026-11-01
The original native implementation updated 32 DWM thumbnail rectangles on the dock thread using WM_TIMER. In the isolated child-window profile it issued 15–20 updates over a 380 ms motion, with gaps up to 67.46 ms. This is not a display FPS measurement. Microsoft's DWM documentation describes preserving source aspect ratio (https://learn.microsoft.com/en-us/archive/msdn-magazine/2007/april/aero-glass-create-special-effects-with-the-desktop-window-manager); independent thumbnail strips cannot represent a continuously warped surface, which remains a visual limitation.

The new timing prototype uses a high-resolution waitable timer and a separate frame worker, coalesces lifecycle messages to the UI, and falls back to WM_TIMER. It blends the lamp phases smoothly and starts the real restore only when the ghost reaches the full window, avoiding early exposure around the ghost. In a final isolated test that held the UI thread busy for 200 ms, the renderer made 48/49 submissions, with max gaps 10.63/12.61 ms. This does not measure presented FPS or guarantee 60 FPS under load. Geometry continuity, reduced motion, restore timing, 12 interrupted animations, and low-resolution timer fallback passed.

A window-only PrintWindow experiment on the synthetic child showed the painted image while visible but zero matching painted pixels after minimize. A GPU mesh based on a snapshot taken only after the minimize event would therefore be unreliable. A correct solution still needs a reliable, nonblocking pre-minimize/live capture strategy and coherent GPU mesh; visual shape, screenshot fidelity, real app coverage, and actual presented FPS remain UNVERIFIED. The timing prototype was not installed and the running shell was not restarted.

Safety follow-up before installation: the prototype limits cleanup waiting to 50 ms and defers resource cleanup if the render worker stalls; an isolated 200 ms simulated stall returned control in 62 ms. The existing `swoop_test.cpp` screen-pixel fixture was not run because of the standing no-screenshots instruction; the synthetic no-screen-capture fixture was used instead. The fixed 32-thumbnail renderer is still an approximation, not a continuous mesh. Do not treat this build as a finished visual fix.

Final isolated profile after bounded cleanup: 45/48 submissions, largest gaps 28.56/10.31 ms, and restore callback at 391 ms. The 28.56 ms gap misses a 16.67 ms frame budget, so even submission timing is not consistently 60 Hz; desktop presentation FPS remains unmeasured. Forced WM_TIMER fallback and 12 repeated interrupted-animation cleanup cases passed; a simulated 200 ms renderer stall returned cleanup in 62 ms. Further renderer work remains necessary before installation.

## Smoothness pass, 2026-11-01 (13:12)
Cause found by porting the lamp math and printing the top-edge step per 60 Hz frame: time was eased with smoothstep AND the stretch/collapse phases were each smoothstepped on top, so the top edge sat still for the first ~25% (frames 1-5), then jumped up to 103 px/frame, then crawled through a sliver for the last ~15%. Now `p` is linear in time and the two phase eases do the shaping: motion starts by frame 3, peak 49 px/frame at 500 ms (480 ms shipped), no dead tail. One shared timeline (`kLampSeconds`, phase edges, `LampOpacity`) in `lamp_geometry.h` replaces three copies in swoop.cpp / swoop_compositor.cpp / tests. Strips overlap by 1 px (no hairline gaps). Dock hold 620 -> 750 ms. Tests: lamp geometry failures 0 (curve fit error 1.33 -> 0.36 px), lamp smoke failures 0, restore callback at 500 ms. Installed; previous exe in `%LOCALAPPDATA%\Halo\app-backup-genie-smooth-20261101\halo.exe`. Visual quality is UNVERIFIED by me (no screenshots taken); judge it by eye.

## Restore blink fixed, 2026-11-01 (13:48)
Reproduced with `tools/swoop_handoff_probe.cpp` (new): it samples a 24x24 patch of the composed screen every ~16 ms across a dock restore of a synthetic red window. Before: 2 of 3 rounds dropped to 0% red for exactly one frame at the instant the real window was restored. Making the overlay outlive `IsIconic` did not help (the drop sat at the restore call itself), so the cause is the live DWM thumbnail going blank for a frame when its source leaves the minimized state. Cloaking the window to avoid it is refused out-of-process (`DwmSetWindowAttribute(DWMWA_CLOAK)` on a foreign window: 0x80070005).
Fix: `Swoop::Restore` now restores the real window at the START of the grow, parked off-screen (`ParkMinimized`: placement shifted left of the virtual screen), when the ghost is still fully transparent (restore fade-in begins at t~8%). The ghost shows the live restored window the whole way up; at t=1 the window slides home (`MoveHome`) under a pixel-identical ghost, which then stays 48 ms (`kSettleMs`) before it is destroyed. Windows that restore maximized can't be parked and keep the old late restore. `End()` always moves a parked window home (interrupts can't strand it). Result: 0 dropouts in 32 probe rounds (8 rounds x 4 runs), window back at 200,100 500x400 every time; minimize start: 0 non-red samples in the first 120 ms. Strips 48 -> 64. Display is 60 Hz (Win32_VideoController), so 480 ms = 29 presented frames; DWM presents every one. Visual quality on real apps (Chromium/Electron repaint after restore, mixed DPI, multiple monitors, taskbar-less edge cases) is UNVERIFIED.
